PIXELY CAREERS CRM
TASK: COMPLETE COMPLAINT DETAIL DRAWER UX RESTRUCTURE

==================================================
OBJECTIVE
==================================================

The Complaint system is already functional.

DO NOT rebuild Complaints.
DO NOT change the approved Complaint workflow.
DO NOT break nested drawer navigation.
DO NOT change Cloudinary.
DO NOT change Orders, Payments, Reviews, Suggestions or authentication except where complaint relationships are displayed.

THIS TASK IS SPECIFICALLY TO REDESIGN AND RESTRUCTURE THE COMPLAINT DETAIL DRAWER SO THAT IT READS LIKE A PROFESSIONAL CASE RECORD.

Current problem:

Complaint information is technically available, but the drawer feels mixed and unstructured.

Important information such as:

- Complaint Category
- Complaint Description
- Complaint Against
- Current Status

does not stand out enough.

Meanwhile:

- Related Order
- Filed By
- Evidence
- Resolution
- Admin Notes
- History

are presented as similar-looking disconnected blocks.

Admin Notes are especially wrong because an existing note is being loaded inside the editable textarea, making it look like placeholder/editable content instead of a historical saved note.

We need a clear visual and information hierarchy.

==================================================
CORE DESIGN PRINCIPLE
==================================================

The drawer should tell the user this story in order:

1. WHAT IS THE COMPLAINT?
2. WHO IS IT AGAINST?
3. WHAT DID THE CLIENT REPORT?
4. WHAT EVIDENCE EXISTS?
5. WHICH ORDER IS INVOLVED?
6. WHAT DECISION DID MANAGEMENT MAKE?
7. HOW WAS IT RESOLVED?
8. WHAT INTERNAL NOTES WERE ADDED?
9. WHAT HAPPENED THROUGHOUT THE CASE?

The user should not have to visually search through random cards.

==================================================

Use this exact information order:

1. HEADER

3. COMPLAINT DESCRIPTION

==================================================
IMPORTANT ADMIN NOTE BEHAVIOR
==================================================

The input area must ALWAYS begin empty.

Placeholder:

"Write an internal note..."

NEVER preload the previous saved note into this field.

When Admin adds a note:

1. Save it as a new historical note.
2. Clear the textarea.
3. Add the note above/below according to chronology.
4. Record actor.
5. Record timestamp.
6. Create a History event.

Do not overwrite previous notes.

==================================================
MULTIPLE ADMIN NOTES
==================================================

The system must support MULTIPLE notes.

Example:

Note 1:
"Client requested another revision."

Note 2:
"Designer confirmed the requested correction."

Note 3:
"Client approved the final version."

These are separate records.

Do not keep one complaint.admin_notes text field that gets overwritten again and again.

==================================================
DATABASE FOR ADMIN NOTES
==================================================

Migrate any existing non-empty admin_notes into complaint_notes as an initial historical note where safely possible.
